Raft lets a group of servers act like one reliable machine. They agree on a single ordered log of commands, so every server computes the same result, and the group keeps working as long as most of its servers are up. This page explains each part of Raft. Why it's needed

The problem Raft solves

Machines crash, disks die and networks drop or delay messages. A service that must not lose data, like bank balances, a database, or the configuration of a whole Kubernetes cluster, can't live on one machine. So we keep copies on several machines. But copies bring a new problem: keeping them identical when failures happen at the worst possible moment.

Option 1: one server

Simple, and there's only ever one answer. But if it crashes, the whole service stops. If its disk dies, the data is gone. It is a single point of failure.

Option 2: copies that don't agree

Every copy accepts changes on its own. When the network splits, both sides keep going and accept conflicting changes. The same 500 gets paid twice, and afterward there's no correct answer about the balance. This is called split brain.

Option 3: copies + consensus

The copies agree on one order of changes, and a change only counts once a majority has it. Two sides of a split can never both have a majority, so they can never both decide. With 5 servers the service keeps working while any 3 are up. This is what Raft does.

Why agreeing is hard

  • Messages can be lost, delayed, duplicated or arrive out of order.
  • Servers can crash at any moment and come back later with old information.
  • There is no shared clock, and a crashed server looks exactly like a slow one.

Why Raft in particular

Paxos solved consensus first, but it is famously hard to understand and to build correctly. Raft (Ongaro and Ousterhout, 2014) gives the same guarantees and was designed to be easy to understand. It splits the problem into leader election, log replication and safety. Today it runs inside etcd (Kubernetes' data store), Consul, CockroachDB, TiKV and Kafka's KRaft mode (a Raft variant).

The goal

A replicated state machine

Each server has three parts: a consensus module, a log and a state machine, such as a key-value store. Clients send commands like x←7. The consensus module makes sure every server's log ends up holding the same commands in the same order.

Each state machine applies committed commands from its log in order. Same commands in the same order means the same state on every server. If one server dies, the others have identical data.

Real-world example

A bank with five ATM booths

Picture a bank with five ATM booths, each keeping its own copy of the transaction ledger. The rule is simple: no booth may hand out the same money twice, even if a booth breaks or the network cable is cut. Each booth is one Raft server. This is a teaching analogy: real ATMs work differently (see the note at the end), but the story maps one-to-one onto Raft.

  1. Morning: choosing a head booth

    All five booths start as followers with a random timer. Booth 3's timer runs out first. It starts shift 1, asks the others for votes, gets 3 and becomes head booth. From now on it pings every booth to say it's still open.

    Leader election · term 1

  2. Alice withdraws 500

    Alice's account holds 1,000. She asks Booth 1 for 500. Booth 1 isn't the head, so it forwards the request to Booth 3. Booth 3 writes Alice −500 as line 4 of its ledger and sends the line to every booth. Booths 1 and 4 write it down and confirm. That makes 3 of 5, so the line is committed and Booth 1 dispenses the cash. Every booth's balance for Alice becomes 500.

    Log replication · commit

  3. The head booth loses power

    Booth 3 goes dark and the pings stop. Booth 4's timer runs out first. It starts shift 2 and asks for votes. Booths 1, 2 and 5 agree, so Booth 4 becomes the new head booth. Booth 4 already has line 4. A booth missing that line couldn't win, because booths that have it refuse to vote for a booth with an older ledger. Alice's withdrawal is never forgotten.

    Timeout · new term · voting rule

  4. The network cable is cut

    Booth 3 is back on, but a cut cable splits {Booth 1, Booth 2} from {Booth 3, 4, 5}. Alice and Bob share the account, which now holds 500. At the same moment Alice asks Booth 1 for 500 and Bob asks Booth 5 for 500. Booths 1 and 2 can only gather 2 votes, so their side never gets a head booth and Alice's request just waits. On the other side, head booth 4 gets 3 of 5 confirmations and Bob gets his 500. The money is paid out once, not twice.

    Partition · majority wins

  5. The cable is repaired

    Booths 1 and 2 hear from head booth 4 and copy Bob's withdrawal into their ledgers. Alice's request was never committed, so there's nothing to undo. When she retries, every booth agrees the balance is 0 and declines it.

    Log repair · consistency

The point: Raft prefers being right to being always available. The smaller side of a split refuses to act rather than risk paying the same money twice.

How real banks differ: a real ATM is just a terminal. It keeps no ledger and never votes. It sends each request through a card network to the bank's core banking system, and that backend is where data is replicated. Older cores often run on mainframes with synchronous replication. Some newer ones run on distributed databases such as CockroachDB or Google Spanner, which use Raft or Paxos inside. Real ATM networks also make the opposite trade-off at times: when the bank can't be reached, "stand-in" processing may approve small withdrawals and reconcile them later, accepting a small risk of overdraft to stay available.

Component · Server roles

Follower, candidate, leader

Every server is in exactly one of three roles. In normal operation there is one leader and all the others are followers.

Follower

Passive. It answers requests from leaders and candidates and never starts a conversation. If it hears nothing for a while, it becomes a candidate.

Candidate

Trying to become leader. It votes for itself and asks every other server for a vote.

Leader

Handles every client request, appends commands to its log, copies them to followers and decides when an entry is committed.

Component · Terms

Numbered periods of time

Raft splits time into terms, numbered 1, 2, 3 and up. Each term starts with an election. If a candidate wins, it leads for the rest of that term. If the vote splits, the term ends with no leader and a new term starts soon after.

Terms act as a logical clock. Every message carries the sender's term:

  • A server that sees a higher term adopts it at once. A leader or candidate that sees one steps down to follower.
  • A request with a lower term is stale and gets rejected.

This is how a leader that was cut off finds out the world has moved on.

Component · Timers and heartbeats

How servers notice a dead leader

Every follower runs an election timer. Each message from the current leader resets it. When the leader has nothing new to send, it still sends empty AppendEntries messages called heartbeats, just to say "I'm alive".

If the timer runs out, the follower assumes the leader is gone and starts an election. Each timeout is randomized, so usually one server times out well before the others, wins and sends heartbeats before anyone else tries. This is what makes split votes rare.

Component · The log

Entries, indexes and commitment

The log is a list of entries. Each entry has an index (its position, starting at 1), the term in which a leader created it, and a command.

An entry is committed once the leader that created it has stored it on a majority of servers. A committed entry will never be lost or changed, so the state machine can safely apply it. Each server tracks the highest committed index it knows of as commitIndex.

Entries past the commit index can still be overwritten by a later leader. In the figure, index 6 is only on S1 and S2. If S1 crashed now, a new leader could replace it.

Component · The two RPCs

Only two kinds of message

Basic Raft needs only two remote procedure calls. Each has a reply, and every message carries the sender's term.

RequestVote

Sent by a candidate to every other server to ask for a vote.

termThe candidate's term
candidateIdWho is asking
lastLogIndexIndex of the candidate's last log entry
lastLogTermTerm of that entry

Reply: term, voteGranted

Grant the vote only if the server hasn't voted for anyone else this term and the candidate's log is at least as up to date as its own. A log is more up to date if its last entry has a higher term. If the terms are equal, the longer log wins.

AppendEntries

Sent by the leader to copy log entries. With no entries, it is a heartbeat.

termThe leader's term
leaderIdSo followers can redirect clients
prevLogIndexIndex of the entry just before the new ones
prevLogTermTerm of that entry
entries[]New entries to store (empty for a heartbeat)
leaderCommitThe leader's commitIndex

Reply: term, success

Accept only if the follower has an entry at prevLogIndex with term prevLogTerm. This consistency check means a follower only accepts entries that continue a matching history. On rejection, the leader steps back one entry and tries again.

Component · Events and rules

Every message and the rule behind it

These are the seven shapes you see moving between servers in the simulator. Each one is sent or answered according to a fixed rule. The simulator's "What just happened" log shows the rule each time it applies.

RequestVote

Sent when a follower's election timer runs out without hearing from a leader.

Rule: the server becomes a candidate, adds 1 to its term, votes for itself, resets its timer and asks every other server for a vote. It wins with votes from a majority (3 of 5). If the timer runs out again first, it starts a new election in a higher term.

Vote granted

Sent when a server agrees to support the candidate.

Grant only if all three hold:
  • The candidate's term is not lower than the voter's term.
  • The voter has not voted for a different server in this term.
  • The candidate's log is at least as up to date: its last entry has a higher term, or the same term and the log is at least as long.
Granting a vote also resets the voter's election timer.

Vote refused

Sent when any one of the grant conditions fails.

Refuse if:
  • Stale term: the candidate's term is lower than the voter's.
  • Already voted: one vote per term, first come first served. A candidate has already voted for itself. This keeps it to one leader per term.
  • Log behind: the candidate could be missing committed entries, so it must not become leader (election restriction).

Heartbeat

Sent when the leader has no new entries for a follower. It is an AppendEntries with an empty list, sent at a fixed interval shorter than any election timeout.

Rule: a follower that receives a heartbeat from a current leader resets its election timer and stays a follower. A candidate that receives one in a term at least as high as its own steps back to follower. The heartbeat also carries the leader's commitIndex, so followers learn which entries are committed.

AppendEntries with 2 entries

Sent when the leader has entries a follower doesn't have yet. The number is how many entries the message carries.

Rule: the leader sends the entries starting at that follower's nextIndex, together with prevLogIndex and prevLogTerm, which describe the entry just before them. An entry is committed once it is stored on a majority and is from the leader's current term.

Append accepted

Sent when the follower stores the entries (or accepts the heartbeat).

Accept only if both hold:
  • The leader's term is not lower than the follower's term.
  • Consistency check: the follower has an entry at prevLogIndex whose term equals prevLogTerm.
If a stored entry conflicts with a new one (same index, different term), the follower deletes it and everything after it, then appends the leader's entries. The leader then advances matchIndex and nextIndex for that follower.

Append rejected

Sent when either accept condition fails.

Reject if:
  • Stale term: the sender is an old leader. The reply carries the newer term, and the old leader steps down to follower.
  • Consistency check fails: the follower has no entry at prevLogIndex, or that entry has a different term. The leader lowers nextIndex by one and retries until the logs match.

Component · Client requests

Reads and writes

A client is whoever uses the cluster, such as an app storing data. It sends two kinds of request. A write changes state, so it must go through the log. A read changes nothing, so it skips the log, but the leader still has to prove its answer isn't out of date.

Write, e.g. x←7

Rule:
  • The leader appends the command to its log as a new entry in its current term.
  • It sends the entry to followers with AppendEntries.
  • Once a majority has stored it, the entry is committed. The leader applies it and replies to the client.

Read, e.g. get x

A leader can't just answer from its own state. It might have been replaced during a partition without knowing, and would return an old value.

Rule (ReadIndex):
  • The leader must have committed an entry in its own term. A new leader adds a no-op entry for this.
  • It records readIndex = its commitIndex.
  • It sends a heartbeat round and waits for replies from a majority. This proves it is still leader.
  • Once its state machine has applied up to readIndex, it answers.
If it can't reach a majority, the read fails instead of returning stale data.

Request sent to a follower

Clients may contact any server, but only the leader serves requests.

Rule: a follower or candidate rejects the request and replies with the leaderId it learned from the latest AppendEntries. The client retries at that server. If no leader is known, for example during an election, the client waits and retries. The hint can be out of date if the leader has just crashed.

Guarantees

Five properties Raft always keeps

The pieces above combine into these guarantees. Together they mean no committed command is ever lost or reordered, whatever crashes or network splits happen.

Election safety
At most one leader per term, because winning needs a majority and each server votes once per term.
Leader append-only
A leader never overwrites or deletes entries in its own log. It only adds to it.
Log matching
If two logs have an entry with the same index and term, the logs are identical up to that entry. The prevLogIndex check enforces this.
Leader completeness
A committed entry is in the log of every later leader. The voting rule makes sure a candidate with an out-of-date log can't win.
State machine safety
If one server applies a command at some index, no server ever applies a different command at that index.
